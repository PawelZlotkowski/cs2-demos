Build a shared Round Reviewer clip labeller with an admin panel and a reviewer panel. Pawel records the gameplay on his Windows PC and uploads selected clips. Reviewers visit the website, enter their personal access code, watch the assigned clips and save observations. Once clips are uploaded, reviewing works while Pawel's PC is off.

This is the implementation and deployment handoff prepared on 17 November 2026. The existing local recorder and labeller were inspected. The cloud panels, code login and publishing workflow described below still need to be built by Claude Code using the accompanying prompt.

The agreed services are Vercel for the existing Next.js application and its small API requests, Cloudflare R2 for private MP4 storage, and Supabase PostgreSQL for accounts, assignments, clip metadata and labels. Reviewer identity is handled by personal access codes and server-side sessions stored in PostgreSQL. Both panels belong to the same application and Vercel project.

The admin uses /label/admin. Reviewers use /label. Everyone enters their code at /label/login, and their account role determines which panel opens. These are proposed routes for the implementation.

The admin panel should provide these actions.

- Add a reviewer using a display name and a unique labeller handle.
- Generate and copy that reviewer's personal login code.
- Activate or deactivate the reviewer, regenerate their code, and sign out their existing sessions.
- Create collections grouped by map, demo and selected player.
- Upload a folder of clips with its generated manifest, see upload progress, retry failures and publish ready clips.
- Assign collections to individual reviewers. The same collection can be assigned to several people so their judgements can be compared.
- See each reviewer's completed and remaining clips, read their notes and export their latest labels.
- Archive a collection when its review is finished.

A reviewer should see their assigned collections and a large Continue reviewing button. Each clip screen needs the video, map, round, selected player's display name, one note box and Save and next. Good play, Needs improvement and Unsure can be optional choices. Keep completion dependent on a written observation, with one save action. Provide replay, playback speed, Skip for now, and an obvious saved or saving indicator. Drafts should survive an interrupted connection and a return to the page. Other people's notes stay hidden during the review.

Use the existing Porcelain visual direction and Mona Sans. Support keyboard operation, a narrow browser window and reduced motion. Reuse the current note-only ClipLabel behaviour and English/Polish language fields.

Personal codes identify accounts.

The admin creates Alex's account and the application generates a random code for Alex. Pawel sends Alex the website address and that code. After Alex logs in, every note is saved against Alex's immutable account ID and stable export handle. The browser supplies the note and clip ID. The server derives the reviewer identity from the authenticated session.

Use a copyable code containing at least 100 bits of cryptographic randomness, formatted into readable groups. Store a keyed hash of the code. Show the raw code only when it is generated. A code remains usable until the admin regenerates it or deactivates the account. Regenerating a code invalidates the old code and existing sessions, while keeping the person's notes and assignments. Reactivation requires a fresh code.

After login, keep a separate random session token in a Secure, HttpOnly, SameSite cookie. Validate the stored session and active account on protected requests. Apply persistent login throttling and same-origin checks to mutations. Keep codes out of URLs and request logs. A bootstrap command run by the owner creates the first admin account and code using the server credentials. Normal account creation in the admin panel creates reviewers.

These details let multiple friends work independently without installing a local application. A shared code would attribute several people's work to the same account, so issue one code per person.

The hosting arrangement is as follows.

- Pawel's PC runs the current demo parser, CS Demo Manager, PostgreSQL for CS Demo Manager, Steam, CS2 and recording worker. It produces H.264 MP4 clips with the existing source evidence.
- Vercel serves the two panels and validates login, assignments, saves and admin actions. It grants narrowly scoped upload and playback access.
- Supabase PostgreSQL stores accounts, code hashes, sessions, collection assignments, clip metadata and versioned notes.
- A dedicated private Cloudflare R2 bucket named cs2-demo-clips holds the MP4s in Standard storage. The browser transfers video directly to and from R2. Supabase stores each clip's object key and metadata.

Vercel functions have a 4.5 MB request-body limit. The uploader sends small manifest and authorisation requests to the app, then transfers the MP4 bytes directly to R2. Use S3 multipart uploads with signed part URLs so interrupted files can resume. The app tracks upload state in PostgreSQL and only publishes ready clips after finalisation checks. [Vercel limits](https://vercel.com/docs/functions/limitations) [R2 uploads](https://developers.cloudflare.com/r2/objects/upload-objects/)

Private playback uses a five-minute presigned GET URL after the server checks the account and assignment. Renew on expiry while preserving playback position. Disabling an account stops new URLs; an existing URL can still work until expiry. Use the R2 S3 endpoint for these links. Keep public r2.dev access disabled and leave public custom domains unconfigured. [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

All application database access runs through the Vercel server. Enable RLS and revoke direct table and RPC access from browser roles. The server secret bypasses RLS, so each server operation must check the caller's role and assignment. Keep source manifests, detector findings, roster identifiers and session records out of reviewer-facing responses. [Supabase database access controls](https://supabase.com/docs/guides/database/postgres/row-level-security)

Your everyday publishing workflow should have four steps.

1. Record the desired demo and player on your PC with the existing labeller.
2. Choose the new Export clips for web action. It writes a host folder containing manifest.json and clips/*.mp4. Choose recordings from a human-readable list of demos, players and batches.
3. Open /label/admin and select that exported folder. The manifest supplies map, player, round, clip identity and source evidence automatically. Upload, preview and publish the collection.
4. Assign reviewers. Send each person the website URL and their own code. Watch progress in the admin panel.

The exporter and upload action are implementation deliverables in the Claude prompt. A .dem file supplies the source on your PC. The hosted review collection consists of recorded clips and the metadata needed to identify them.
